# ห้องสมุดที่ใช้ LLM-Wiki แทนหนังสือแต่ละเล่ม

> งานค้นคว้าเชิงออกแบบ (design research) ว่าด้วยแนวคิดห้องสมุดยุคใหม่ ที่ "หนังสือแต่ละเล่ม"
> ไม่ใช่ไฟล์นิ่ง ๆ อีกต่อไป แต่กลายเป็น **วิกิที่ขับเคลื่อนด้วย LLM** — คุยได้ ถามได้
> สรุปได้ และอ้างอิงกลับไปยังต้นฉบับได้

> ⚠️ ปรับวัตถุประสงค์: เอกสารนี้ตั้งกรอบแบบ **RAG-centric** (หนังสือ = ต้นฉบับ + ดึงตอนถาม)
> ซึ่งถูกปรับใหม่แล้ว ดูกรอบที่ถูกต้อง (Karpathy-style: คอมไพล์ raw เป็น wiki) ได้ที่
> [llm-wiki/00-overview.md](llm-wiki/00-overview.md) เก็บไฟล์นี้ไว้เพื่ออ้างอิงเชิงประวัติ

> หมายเหตุ: เอกสารนี้ต่อยอดจาก [how-library-works.md](how-library-works.md),
> [library-vs-wiki.md](library-vs-wiki.md) และ
> [how-to-build-digital-library.md](how-to-build-digital-library.md)
> ควรอ่านสามชิ้นนั้นก่อนเพื่อเห็นภาพรวม

## 1. แนวคิดหลัก: "หนังสือหนึ่งเล่ม = LLM-Wiki หนึ่งตัว"

ในห้องสมุดแบบดั้งเดิม หนังสือคือ **วัตถุนิ่ง (static object)** — ผู้อ่านต้องเปิดอ่านเอง
ค้นเอง ตีความเอง ส่วนในแนวคิดนี้ เราเปลี่ยน "หนังสือแต่ละเล่ม" ให้เป็น **LLM-Wiki**:

> **LLM-Wiki** = หน่วยความรู้ที่มี (1) เนื้อหาต้นฉบับเป็นฐานข้อมูล (2) โมเดลภาษา (LLM)
> เป็นส่วนต่อประสาน ทำให้ผู้ใช้ "สนทนากับหนังสือ" ได้ — ถามคำถาม ขอสรุป ขอตัวอย่าง
> เปรียบเทียบ โดยทุกคำตอบ **ผูกกลับ (grounded)** ไปยังข้อความจริงในเล่ม

เปรียบเทียบสามยุค:

| ยุค | หน่วยความรู้ | ผู้ใช้ทำอะไร |
|-----|-------------|-------------|
| ห้องสมุดกายภาพ | หนังสือกระดาษ | เดินไปหยิบ เปิดอ่านเอง |
| ห้องสมุดดิจิทัล | ไฟล์ + full-text search | ค้นคำ เปิดอ่านเอง |
| **ห้องสมุด LLM-Wiki** | **เล่ม + LLM ต่อเล่ม** | **ถาม-ตอบ สนทนา ให้ AI ช่วยตีความ** |

**สำคัญ:** นี่ไม่ใช่ "แชตบอตตัวเดียวที่รู้ทุกอย่าง" แต่เป็น **หนึ่ง LLM-Wiki ต่อหนึ่งเล่ม/คอลเลกชัน**
ที่ผูกกับเนื้อหาเฉพาะของเล่มนั้น — รักษาแนวคิดห้องสมุดที่ว่า "ความรู้แต่ละหน่วยมีขอบเขตและที่มาชัดเจน"

## 2. ทำไมต้องทำ (แรงจูงใจ)

| ข้อจำกัดของหนังสือ/ไฟล์นิ่ง | สิ่งที่ LLM-Wiki ช่วยได้ |
|------------------------------|--------------------------|
| ต้องอ่านเองทั้งเล่มกว่าจะเจอคำตอบ | ถามตรงประเด็น ได้คำตอบทันทีพร้อมหน้าอ้างอิง |
| ภาษาทางการ/เก่า เข้าใจยาก | ขอให้อธิบายใหม่ตามระดับผู้อ่าน |
| ค้นได้แค่ "คำที่ตรงตัว" (keyword) | ค้นได้ตาม "ความหมาย" (semantic search) |
| เชื่อมโยงข้ามเล่มยาก | ถามเปรียบเทียบหลายเล่มพร้อมกันได้ |
| ภาษาเดียว | แปล/ตอบข้ามภาษาได้ |
| ผู้พิการทางสายตาเข้าถึงยาก | สนทนาด้วยเสียง สรุปให้ฟังได้ |

แต่ต้องแลกมาด้วยปัญหาใหม่ (ดูหัวข้อ 5) โดยเฉพาะ **ความถูกต้องและการอ้างอิง**

## 3. สถาปัตยกรรม: RAG เป็นแกนกลาง

หัวใจทางเทคนิคคือ **RAG (Retrieval-Augmented Generation)** — แทนที่จะให้ LLM
"ตอบจากความจำ" (ซึ่งมั่ว/ล้าสมัยได้) เราให้มัน **ดึงข้อความจริงจากเล่มมาก่อน แล้วค่อยตอบ**

```
ผู้ใช้ถาม
   │
   ▼
[1] ทำ embedding คำถาม ──► [2] ค้นใน Vector DB ของเล่มนั้น
                                    │ (semantic search)
                                    ▼
                          [3] ดึงข้อความที่เกี่ยวข้อง (chunks)
                                    │
                                    ▼
[5] คำตอบ + อ้างอิงหน้า ◄── [4] LLM สังเคราะห์คำตอบจาก chunks ที่ดึงมา
   (grounded answer)            (พร้อม citation กลับไปต้นฉบับ)
```

### ชั้นการทำงาน (ต่อยอดจากสถาปัตยกรรมห้องสมุดดิจิทัล)

```
┌────────────────────────────────────────────────┐
│  ชั้นสนทนา (Conversation UI)                      │
│  ถาม-ตอบ · สรุป · เปรียบเทียบ · อ่านออกเสียง       │
├────────────────────────────────────────────────┤
│  ชั้น Orchestration / RAG                         │
│  จัดการ prompt · เลือกเล่ม · รวมหลายเล่ม · citation │
├────────────────────────────────────────────────┤
│  ชั้น LLM (Generation)                            │
│  โมเดลภาษา (ตอบโดย "ห้ามออกนอกบริบทที่ดึงมา")       │
├────────────────────────────────────────────────┤
│  ชั้นดัชนีความหมาย (Vector Index)                  │
│  Embeddings + Vector DB (ดัชนีความหมายต่อเล่ม)     │
├────────────────────────────────────────────────┤
│  ชั้นจัดเก็บต้นฉบับ (Source of Truth)              │
│  ข้อความจริง + metadata + เลขหน้า (immutable)      │
└────────────────────────────────────────────────┘
```

**หลักการสำคัญ:** ชั้นล่างสุด (**ต้นฉบับ**) ต้อง **ไม่เปลี่ยนแปลง (immutable)** และเป็น
"แหล่งความจริง (source of truth)" เสมอ — LLM เป็นเพียง "ส่วนต่อประสานที่ฉลาด"
ไม่ใช่ที่เก็บความจริง

## 4. ขั้นตอนการสร้าง (Step by Step)

### ขั้นที่ 1: เตรียมต้นฉบับ (เหมือนห้องสมุดดิจิทัล)
- Digitize + OCR หรือใช้ born-digital
- **เก็บเลขหน้า/ตำแหน่งไว้เสมอ** เพื่อทำ citation กลับได้

### ขั้นที่ 2: แบ่งเนื้อหาเป็นชิ้น (Chunking)
- ตัดเนื้อหาเป็นช่วงพอเหมาะ (เช่น ย่อหน้า/หัวข้อ) แต่ละชิ้นแนบ metadata (เล่ม, บท, หน้า)
- การ chunk ที่ดี = คำตอบแม่นและอ้างอิงตรงจุด

### ขั้นที่ 3: สร้าง Embeddings + Vector Index
- แปลงแต่ละ chunk เป็นเวกเตอร์ด้วยโมเดล embedding
- เก็บใน **Vector Database** (เช่น pgvector, FAISS, Milvus, Qdrant) — หนึ่งดัชนีต่อเล่ม
  หรือรวมทั้งคอลเลกชันแต่กรองตามเล่มได้

### ขั้นที่ 4: ตั้งค่า RAG Pipeline + Prompt
- ออกแบบ system prompt ให้ LLM **"ตอบเฉพาะจากบริบทที่ให้ ถ้าไม่มีให้บอกว่าไม่พบ"**
- บังคับให้แนบ **citation** ทุกครั้ง

### ขั้นที่ 5: ทำชั้น Catalog/Metadata (เหมือนเดิม)
- ยังต้องมี Dublin Core/MARC เพื่อให้ "เลือกเล่ม" และจัดหมวดได้ (ดู digital library doc)

### ขั้นที่ 6: ควบคุมสิทธิ์และที่มา (Provenance & Rights)
- บันทึกว่าคำตอบมาจากเล่มไหน หน้าไหน เวอร์ชันใด
- คุมลิขสิทธิ์: LLM ต้อง "อ้างอิงและสรุป" ไม่ใช่ "ทำซ้ำทั้งเล่ม"

### ขั้นที่ 7: ประเมินคุณภาพ (Evaluation) — ขาดไม่ได้
- ทดสอบความถูกต้อง (faithfulness), ความครบ, อัตราการมั่ว (hallucination rate)
- ใช้ชุดคำถาม-คำตอบมาตรฐานวัดซ้ำทุกครั้งที่เปลี่ยนโมเดล

### ขั้นที่ 8: เปิดบริการ + เก็บ feedback + บำรุงรักษา

## 5. ปัญหาและวิธีแก้ (สำคัญที่สุด)

แนวคิดนี้สร้างพลังมหาศาล แต่ก็เปิดปัญหาใหม่ที่ห้องสมุดต้องรับผิดชอบ:

| ปัญหา | ความเสี่ยง | วิธีแก้ |
|-------|-----------|---------|
| **การมั่ว (Hallucination)** | LLM แต่งคำตอบที่ไม่มีในเล่ม | บังคับ RAG + "ตอบเฉพาะจากบริบท" + แสดง citation ให้ตรวจได้ |
| **ที่มาเลือนหาย (Provenance)** | ผู้ใช้แยกไม่ออกว่าอันไหนต้นฉบับ อันไหน AI ตีความ | แยกแสดงชัด "คำพูดจากเล่ม" vs "บทสรุปโดย AI" + ลิงก์หน้าจริง |
| **อคติของโมเดล (Bias)** | LLM ใส่มุมมองของตัวเองเข้าไป | จำกัด generation, ประเมิน bias, ให้คำตอบอ้างอิงข้อความตรง |
| **ลิขสิทธิ์** | สรุป/ทำซ้ำเกินสิทธิ์ | จำกัดความยาว, แสดงเฉพาะส่วนที่ได้รับอนุญาต, Controlled Digital Lending |
| **ต้นทุน/พลังงาน** | รัน LLM แพงและกินไฟ | ใช้ cache คำตอบที่ถามบ่อย, โมเดลเล็กสำหรับงานง่าย, batch |
| **ความเป็นส่วนตัว** | คำถามผู้ใช้รั่ว/ถูกเก็บ | รันโมเดลในองค์กร (on-prem), ไม่เก็บ log ที่ระบุตัวตน |
| **ความถาวรของคำตอบ** | เปลี่ยนโมเดล คำตอบเปลี่ยน | ต้นฉบับ immutable เป็นหลัก, บันทึกเวอร์ชันโมเดลกับทุกคำตอบ |
| **ความเสื่อมของโมเดล** | โมเดลล้าสมัย/เลิกใช้ | แยกชั้น LLM ออกจากข้อมูล เพื่อสลับโมเดลได้โดยข้อมูลคงอยู่ |

> หลักการกำกับ: **"LLM คือบรรณารักษ์ ไม่ใช่ผู้เขียน"** — มันช่วยค้น สรุป และนำทาง
> แต่ความจริงอยู่ที่ต้นฉบับเสมอ และผู้ใช้ต้องตามไปตรวจได้

## 6. เปรียบเทียบกับรูปแบบเดิม

| มิติ | ห้องสมุดดิจิทัล | Wiki | **ห้องสมุด LLM-Wiki** |
|------|----------------|------|----------------------|
| หน่วยความรู้ | ไฟล์นิ่ง | หน้าที่คนแก้ร่วมกัน | เล่ม + LLM ต่อเล่ม |
| การค้นหา | keyword / full-text | full-text + ลิงก์ | **semantic + สนทนา** |
| ผู้ตีความเนื้อหา | ผู้อ่านเอง | ชุมชนผู้เขียน | **AI ช่วยตีความ (ผูกต้นฉบับ)** |
| ความถูกต้อง | = ต้นฉบับ | ขึ้นกับชุมชน | = ต้นฉบับ **ถ้า** ทำ RAG+citation ดี |
| ความเสี่ยงหลัก | ฟอร์แมตล้าสมัย | vandalism | **hallucination / provenance** |
| แหล่งความจริง | ตัวไฟล์ | เวอร์ชันล่าสุด | **ต้นฉบับ (ไม่ใช่ตัว LLM)** |

จุดต่างกับ "wiki" สำคัญมาก: wiki ให้ **มนุษย์** ร่วมเขียนความรู้ใหม่ ส่วน LLM-Wiki
ให้ **AI ช่วยเข้าถึงความรู้เดิม** โดยไม่แก้ต้นฉบับ — จึงเหมาะกับงานที่ต้องการ
**ความน่าเชื่อถือของห้องสมุด + ความสะดวกของการสนทนา**

## 7. การเทียบเคียงกับวิทยาการคอมพิวเตอร์

| แนวคิด LLM-Wiki | แนวคิดวิทยาการคอมพิวเตอร์ |
|-----------------|---------------------------|
| RAG (ดึงก่อนตอบ) | **Cache-aside / lookup before compute** |
| Vector DB + embeddings | **Approximate Nearest Neighbor search** |
| Semantic search | **Dense retrieval / similarity index** |
| Chunking + metadata | **Indexing granularity / partitioning** |
| ต้นฉบับ immutable + LLM เปลี่ยนได้ | **Separation: data layer vs compute layer** |
| Citation ผูกหน้า | **Provenance tracking / data lineage** |
| Cache คำตอบที่ถามบ่อย | **Memoization** |
| สลับโมเดลได้ | **Dependency injection / pluggable backend** |
| Eval suite วัด hallucination | **Regression testing / quality gate** |

## 8. สรุป

ห้องสมุด LLM-Wiki คือการรวมจุดแข็งของทั้งสามโลก:
- **ความน่าเชื่อถือและการคัดกรอง** ของห้องสมุด
- **การเข้าถึงทุกที่ทุกเวลา** ของห้องสมุดดิจิทัล
- **ความเป็นกันเองและโต้ตอบได้** ของ wiki/แชต

โดยมีกฎเหล็กข้อเดียว: **ต้นฉบับคือความจริง LLM คือบรรณารักษ์ที่พาเราไปหาความจริงนั้น**
ความสำเร็จของระบบนี้ไม่ได้วัดที่ "ตอบเก่งแค่ไหน" แต่วัดที่ **"ตอบแล้วตามกลับไปตรวจต้นฉบับได้แม่นแค่ไหน"**

### เช็กลิสต์สร้างห้องสมุด LLM-Wiki
- [ ] เตรียมต้นฉบับ + เก็บเลขหน้า (immutable source of truth)
- [ ] Chunking พร้อม metadata อ้างอิง
- [ ] สร้าง embeddings + Vector DB ต่อเล่ม
- [ ] วาง RAG pipeline + prompt บังคับ "ตอบจากบริบท + อ้างอิง"
- [ ] คงชั้น catalog/metadata เดิมไว้ (เลือกเล่ม/จัดหมวด)
- [ ] คุมที่มา ลิขสิทธิ์ และความเป็นส่วนตัว
- [ ] ทำ evaluation วัด hallucination ก่อนเปิด
- [ ] แยกชั้น LLM ให้สลับโมเดลได้ + cache คำตอบ
- [ ] เปิดบริการ เก็บ feedback ปรับปรุงต่อเนื่อง
