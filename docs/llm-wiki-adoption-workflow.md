# Workflow การศึกษาและนำ LLM-Wiki มาใช้ (Adoption Study Workflow)

> กระบวนการ (workflow) แบบเป็นขั้นเป็นตอน สำหรับองค์กร/ห้องสมุดที่ต้องการ
> **ศึกษา ทดลอง ประเมิน และตัดสินใจนำ LLM-Wiki มาใช้จริง** — ไม่ใช่แค่
> "อ่านแนวคิด" แต่เป็นเส้นทางทำงานที่มี **จุดตัดสินใจ (decision gate)**,
> **ผู้รับผิดชอบ**, และ **สิ่งส่งมอบ (deliverable)** ในแต่ละเฟส

> ⚠️ ปรับวัตถุประสงค์: workflow นี้อิงกรอบ RAG-centric รุ่นก่อน กรอบที่ถูกต้อง
> (Karpathy-style: ingest→synthesis→lint→query แล้วเก็บเป็นห้องสมุด citation) อยู่ที่
> [llm-wiki/00-overview.md](llm-wiki/00-overview.md) — เก็บไฟล์นี้ไว้เพื่ออ้างอิงเชิงประวัติ

> หมายเหตุ: เอกสารนี้ต่อยอดจาก [llm-wiki-library.md](llm-wiki-library.md)
> (แนวคิดและสถาปัตยกรรม) และ [how-to-build-digital-library.md](how-to-build-digital-library.md)
> ควรอ่านสองชิ้นนั้นก่อนเพื่อเข้าใจศัพท์อย่าง RAG, embedding, citation

---

## 0. ขอบเขต: "LLM-Wiki" ไม่ใช่ "Web Wiki"

ก่อนเริ่ม workflow ต้องตกลงนิยามให้ตรงกันก่อน เพราะคำว่า "wiki" ทำให้เข้าใจผิดได้ง่าย:

| มิติ | **LLM-Wiki** (สิ่งที่เราจะศึกษา) | Web Wiki (สิ่งที่ **ไม่ใช่**) |
|------|-------------------------------|------------------------------|
| ใครสร้างเนื้อหา | ต้นฉบับนิ่ง (เล่ม/เอกสาร) + LLM ช่วย "เข้าถึง" | มนุษย์ช่วยกัน "เขียน/แก้" เนื้อหา |
| แก้ต้นฉบับได้ไหม | **ไม่** ต้นฉบับ immutable | ได้ ใครก็แก้หน้าได้ |
| วิธีใช้งาน | **สนทนา ถาม-ตอบ** กับเล่ม (RAG + citation) | อ่าน/แก้หน้า ตามลิงก์ |
| แหล่งความจริง | ต้นฉบับเสมอ (LLM แค่บรรณารักษ์) | เวอร์ชันล่าสุดของหน้า |
| ความเสี่ยงหลัก | hallucination / provenance | vandalism / edit war |

> **กฎเหล็กที่ต้องถือตลอด workflow:** *"ต้นฉบับคือความจริง LLM คือบรรณารักษ์"*
> ทุกการตัดสินใจในเฟสถัด ๆ ไปต้องไม่ละเมิดหลักนี้

## 1. ภาพรวม Workflow

```
            ┌─────────────────────────────────────────────┐
            │  หลักการกำกับ: ต้นฉบับ = ความจริง, LLM = ตัวช่วย │
            └─────────────────────────────────────────────┘
                              │
  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
  │ เฟส 1  │──▶│ เฟส 2  │──▶│ เฟส 3  │──▶│ เฟส 4  │──▶│ เฟส 5  │──▶│ เฟส 6  │
  │ กรอบ   │   │ สำรวจ  │   │ Pilot  │   │ ประเมิน│   │ ขยายผล │   │ ดูแล   │
  │ โจทย์  │   │ +ออกแบบ│   │ (POC)  │   │ +ตัดสิน│   │ (Scale)│   │ ต่อเนื่อง│
  └────────┘   └────────┘   └────────┘   └────────┘   └────────┘   └────────┘
       │            │            │            │            │            │
     Gate A       Gate B       Gate C       Gate D       Gate E       (loop)
   "ควรทำ?"     "ทำได้?"     "เวิร์ก?"   "ปลอดภัย/    "พร้อม      "ยังดีอยู่?"
                                          คุ้มไหม?"    ขยายไหม?"
```

แต่ละเฟสมี **Gate** คั่น — ถ้าไม่ผานเกณฑ์ของ gate ให้ **หยุด/ถอย/ปรับ** ไม่ใช่ดันต่อ
(หลักเดียวกับ stage-gate ในการบริหารโครงการ และ quality gate ในวิศวกรรมซอฟต์แวร์)

## 2. เฟส 1 — กรอบโจทย์ (Framing)

**คำถามนำการศึกษา:** เราจะแก้ปัญหาอะไร ให้ใคร และวัดความสำเร็จอย่างไร?

### กิจกรรม
- ระบุ **ผู้ใช้เป้าหมาย** และ use case จริง (เช่น นักวิจัยค้นงานเก่า, ผู้พิการทางสายตา
  ฟังสรุป, นักเรียนถามเนื้อหาในตำรา)
- กำหนด **ตัวชี้วัดความสำเร็จ** ตั้งแต่ต้น — เน้น *"ตามกลับไปตรวจต้นฉบับได้แม่นแค่ไหน"*
  ไม่ใช่ *"ตอบลื่นแค่ไหน"*
- ตีกรอบ **คลังเอกสารตั้งต้น** (corpus) ที่จะเอามาทดลอง — เล็ก ชัด และมีสิทธิ์ใช้

### Deliverable
- เอกสารโจทย์ (problem statement) 1 หน้า + รายการ use case จัดลำดับความสำคัญ
- นิยาม metric (เช่น faithfulness, citation accuracy, answer coverage)

### ✅ Gate A — "ควรทำไหม?"
- [ ] มี use case ที่ keyword/full-text search เดิม **แก้ไม่ได้ดีพอ** (คุ้มที่จะใช้ LLM)
- [ ] มี corpus ที่ **มีสิทธิ์ใช้** และเก็บเลขหน้า/ตำแหน่งได้
- [ ] ผู้มีอำนาจตัดสินใจยอมรับ metric "วัดที่การอ้างอิงต้นฉบับ"

> ถ้าปัญหาแก้ได้ด้วย full-text search ธรรมดา → **ไม่ต้องใช้ LLM-Wiki** (อย่าใช้เพราะมันเท่)

## 3. เฟส 2 — สำรวจและออกแบบ (Survey & Design)

**คำถามนำ:** สถาปัตยกรรมและเครื่องมือแบบไหน ที่ตอบโจทย์เฟส 1 ได้?

### กิจกรรม
- ทบทวนสถาปัตยกรรม RAG 5 ชั้นจาก [llm-wiki-library.md §3](llm-wiki-library.md)
  (สนทนา → orchestration/RAG → LLM → vector index → ต้นฉบับ immutable)
- เลือกแนวทางเชิงเทคนิคแบบ **เปรียบเทียบ ไม่ใช่ผูกขาด**:

| จุดตัดสินใจ | ทางเลือก | เกณฑ์เลือก |
|------------|---------|-----------|
| Embedding model | multilingual vs เฉพาะภาษาไทย | คุณภาพ semantic บนภาษาเอกสารจริง |
| Vector DB | pgvector / FAISS / Qdrant / Milvus | สเกล, ใช้ของเดิมได้ไหม, on-prem ได้ไหม |
| LLM | cloud API vs on-prem (เปิด) | ความเป็นส่วนตัว, ต้นทุน, คุณภาพ |
| Chunking | ตามย่อหน้า/หัวข้อ/ขนาดคงที่ | คำตอบแม่น + อ้างอิงตรงจุด |
| Index ต่อเล่ม vs รวม | แยกต่อเล่ม / รวมแล้วกรอง | ขอบเขตความรู้ชัด vs ค้นข้ามเล่ม |

- ออกแบบ **prompt บังคับ grounding** — "ตอบเฉพาะจากบริบทที่ดึงมา ถ้าไม่มีให้บอกว่าไม่พบ"
  และ "แนบ citation ทุกครั้ง"
- ออกแบบ **ชุดทดสอบ (eval set)**: คำถาม–คำตอบอ้างอิง (พร้อมหน้าที่ถูกต้อง) อย่างน้อย ~30–50 ข้อ

### Deliverable
- เอกสารออกแบบสถาปัตยกรรม + ตารางเปรียบเทียบเครื่องมือ + เหตุผลที่เลือก
- Eval set เวอร์ชันแรก (เป็น "ข้อสอบ" ที่จะใช้ซ้ำทุกครั้งที่เปลี่ยนโมเดล)

### ✅ Gate B — "ทำได้ทางเทคนิคไหม?"
- [ ] เลือก stack ได้ครบทุกชั้น พร้อมเหตุผล
- [ ] มี eval set พร้อม "เฉลย" ที่ผูกหน้าจริง
- [ ] ออกแบบทางแยกชั้น LLM ออกจากข้อมูล (สลับโมเดลภายหลังได้)

---

## 4. เฟส 3 — ทำต้นแบบ (Pilot / POC)

**คำถามนำ:** บนเล่มจริงจำนวนน้อย ระบบ "เวิร์ก" หรือไม่?

### กิจกรรม (ตาม pipeline สร้างใน [llm-wiki-library.md §4](llm-wiki-library.md))
1. เตรียมต้นฉบับ 1–3 เล่ม + เก็บเลขหน้า (immutable)
2. Chunking + แนบ metadata (เล่ม/บท/หน้า)
3. สร้าง embeddings → ใส่ Vector DB
4. ต่อ RAG pipeline + prompt grounding + citation
5. ทำ UI สนทนาแบบ minimal (ถาม-ตอบ + แสดง citation/ลิงก์หน้า)

### หลักสำคัญระหว่าง pilot
- แยกแสดงให้ชัด **"คำพูดจากเล่ม" vs "บทสรุปโดย AI"** + ลิงก์หน้าจริงทุกครั้ง
- ขอบเขตเล็กไว้ก่อน — ยังไม่ต้อง optimize ต้นทุน/สเกล

### Deliverable
- ต้นแบบใช้งานได้จริงบน corpus เล็ก + log การถาม-ตอบสำหรับวิเคราะห์

### ✅ Gate C — "เวิร์กไหม?"
- [ ] ถามคำถามใน eval set แล้ว **ดึง chunk ถูกเล่ม/ถูกหน้า** เป็นส่วนใหญ่
- [ ] คำตอบ **มี citation ที่ตามกลับไปตรวจได้จริง**
- [ ] เมื่อเนื้อหาไม่มีในเล่ม ระบบ **บอกว่า "ไม่พบ"** แทนที่จะมั่ว

---

## 5. เฟส 4 — ประเมินและตัดสินใจ (Evaluate & Decide)

**คำถามนำ:** ระบบ *ถูกต้อง ปลอดภัย และคุ้มค่า* พอจะใช้จริงไหม?

### วัดเชิงคุณภาพคำตอบ
| Metric | วัดอะไร | ผ่านเมื่อ |
|--------|---------|-----------|
| Faithfulness | คำตอบยึดตามบริบทที่ดึงมาจริง | สูง (มั่วต่ำ) |
| Citation accuracy | หน้าที่อ้างถูกต้อง | สูง |
| Retrieval recall | ดึง chunk ที่เกี่ยวข้องครบ | สูงพอที่จะตอบครบ |
| Hallucination rate | สัดส่วนคำตอบที่แต่งเอง | ต่ำกว่าเกณฑ์ที่ตั้งไว้ |

### ตรวจความเสี่ยง (อ้างอิง [llm-wiki-library.md §5](llm-wiki-library.md))
- **Provenance:** ผู้ใช้แยกออกไหมว่าอันไหนต้นฉบับ อันไหน AI ตีความ
- **ลิขสิทธิ์:** สรุป/อ้างอิงเท่านั้น ไม่ทำซ้ำทั้งเล่ม
- **ความเป็นส่วนตัว:** คำถามผู้ใช้ถูกเก็บ/รั่วไหม
- **ต้นทุน/พลังงาน:** ประมาณการต่อคำถาม + ทางลด (cache, โมเดลเล็ก, batch)

### Deliverable
- รายงานผลประเมิน (ตัวเลข metric + การวิเคราะห์ความเสี่ยง + ประมาณการต้นทุน)
- ข้อเสนอ go / no-go / pivot

### ✅ Gate D — "ปลอดภัยและคุ้มไหม?"
- [ ] Metric คุณภาพผ่านเกณฑ์ที่ตั้งในเฟส 1
- [ ] ความเสี่ยงด้านลิขสิทธิ์/ความเป็นส่วนตัวมีมาตรการรองรับ
- [ ] ต้นทุนต่อคุณค่าที่ได้ อยู่ในระดับที่องค์กรรับได้

> ผ่าน → ไปเฟส 5 · ไม่ผ่านบางจุด → กลับไปปรับเฟส 2–3 · ไม่คุ้มเลย → **หยุดอย่างมีข้อมูล**

## 6. เฟส 5 — ขยายผล (Scale)

**คำถามนำ:** จะขยายจาก "ไม่กี่เล่ม" ไปสู่ "ทั้งคอลเลกชัน" อย่างมีระเบียบได้อย่างไร?

### กิจกรรม
- ทำ **pipeline นำเข้าเล่มใหม่** ให้ทำซ้ำได้ (digitize → chunk → embed → index)
- คงชั้น **catalog/metadata** เดิม (Dublin Core/MARC) เพื่อ "เลือกเล่ม"/จัดหมวด
- เพิ่มความสามารถข้ามเล่ม (เปรียบเทียบหลายเล่ม) ถ้าโจทย์ต้องการ
- วาง **provenance & rights**: บันทึกว่าคำตอบมาจากเล่ม/หน้า/เวอร์ชันโมเดลใด
- ใส่กลไกลดต้นทุน: cache คำตอบที่ถามบ่อย, เลือกขนาดโมเดลตามงาน

### ✅ Gate E — "พร้อมเปิดกว้างไหม?"
- [ ] นำเข้าเล่มใหม่ได้แบบกระบวนการซ้ำได้ ไม่ต้องทำมือทุกครั้ง
- [ ] ทุกคำตอบบันทึก provenance (เล่ม/หน้า/เวอร์ชันโมเดล)
- [ ] มีระบบเก็บ feedback จากผู้ใช้

---

## 7. เฟส 6 — ดูแลต่อเนื่อง (Operate & Maintain)

**คำถามนำ:** เมื่อโมเดล/ข้อมูลเปลี่ยน ระบบยัง "ดีอยู่" ไหม?

### กิจกรรมวนซ้ำ
- รัน **eval set เดิมซ้ำทุกครั้งที่เปลี่ยนโมเดล/embedding** (regression test)
- เฝ้าดู hallucination rate และ feedback เชิงลบ
- เมื่อโมเดลล้าสมัย/เลิกใช้ → **สลับโมเดลโดยข้อมูลคงอยู่** (ผลจากการแยกชั้นในเฟส 2)
- ทบทวนสิทธิ์/ลิขสิทธิ์/ความเป็นส่วนตัวเป็นรอบ

> ต้นฉบับ immutable ทำให้ "ความถาวรของความจริง" ไม่ผูกกับอายุของโมเดล —
> โมเดลเป็นของเปลี่ยนได้ ข้อมูลเป็นของถาวร

---

## 8. ผู้รับผิดชอบ (ใครทำอะไร)

| บทบาท | รับผิดชอบหลักในเฟส |
|-------|---------------------|
| บรรณารักษ์/ผู้ดูแล corpus | 1, 3, 5 (เลือกเล่ม, สิทธิ์, metadata, provenance) |
| วิศวกร/ทีมเทคนิค | 2, 3, 5, 6 (สถาปัตยกรรม, pipeline, สเกล, ดูแล) |
| ผู้เชี่ยวชาญประเมิน/QA | 2, 4, 6 (eval set, วัดผล, regression) |
| ฝ่ายกฎหมาย/compliance | 1, 4, 5 (ลิขสิทธิ์, ความเป็นส่วนตัว) |
| ผู้บริหาร/เจ้าของงบ | Gate A และ Gate D (go/no-go) |

---

## 9. เช็กลิสต์รวบยอด (Workflow ทั้งเส้น)

- [ ] **เฟส 1** มีโจทย์ชัด + metric ที่วัด "การอ้างอิงต้นฉบับ" → ผ่าน Gate A
- [ ] **เฟส 2** เลือก stack + prompt grounding + สร้าง eval set → ผ่าน Gate B
- [ ] **เฟส 3** pilot บนเล่มจริง ดึงถูกหน้า + citation ตรวจได้ → ผ่าน Gate C
- [ ] **เฟส 4** วัด faithfulness/hallucination + ตรวจความเสี่ยง/ต้นทุน → ผ่าน Gate D
- [ ] **เฟส 5** pipeline นำเข้าเล่มซ้ำได้ + provenance ครบ → ผ่าน Gate E
- [ ] **เฟส 6** รัน eval ซ้ำเมื่อเปลี่ยนโมเดล + สลับโมเดลได้โดยข้อมูลคงอยู่
- [ ] ตลอดเส้น: ยึดกฎ **"ต้นฉบับคือความจริง LLM คือบรรณารักษ์"** ไม่เคยละเมิด
