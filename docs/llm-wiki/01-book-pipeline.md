## 1. ภาพรวมไปป์ไลน์

ไปป์ไลน์คือ "โรงงานผลิตเล่ม" ที่รับ **raw หลายแหล่ง** (papers, โน้ต, โค้ด, บทสนทนา,
หน้าเว็บ) แล้วทยอยแปลงเป็น **หน้า wiki** ที่เชื่อมโยงกัน โดยมี **schema** เป็นกติกาควบคุม
พฤติกรรมของ LLM ในทุกสเตจ (schema = "สเปกของคอมไพเลอร์" ดูชั้น 2)

```
        แหล่งความรู้ดิบหลายที่
   (papers · โน้ต · โค้ด · บทสนทนา · เว็บ)
                  │
                  ▼
        ┌───────────────────┐
        │   1. INGEST       │  นำเข้า + ย่อย source ทีละชิ้น
        │                   │  เก็บลง raw/ (immutable) + append log
        └─────────┬─────────┘
                  ▼
        ┌───────────────────┐
        │   2. SYNTHESIS    │  "คอมไพล์": LLM เขียน/อัปเดตหน้า wiki
        │                   │  (summary · entity · concept · index)
        └─────────┬─────────┘   1 source แตะ ~10–15 หน้า
                  ▼
        ┌───────────────────┐
        │   3. LINT         │  ตรวจสุขภาพ wiki เป็นรอบ ๆ
        │                   │  ขัดแย้ง · ล้าสมัย · กำพร้า · ลิงก์ขาด · ช่องว่าง
        └─────────┬─────────┘
                  ▼
        ┌───────────────────┐
        │   4. QUERY        │  ถาม-ตอบจากหน้า wiki ที่สังเคราะห์ไว้
        │                   │  คำตอบดี ๆ ถูก file back เป็นหน้าใหม่
        └─────────┬─────────┘
                  │
                  └──────► ป้อนกลับเข้า synthesis → ความรู้ COMPOUND
```

> สเตจ **synthesis** คือหัวใจที่ทำให้ ingest กลายเป็น "การคอมไพล์" จริง ๆ —
> Karpathy รวม ingest/synthesis เป็นจังหวะเดียว ("อ่าน source แล้วเขียนหน้า")
> ในชุดนี้เราแยกชื่อให้เห็นชัดว่า *การนำเข้า* กับ *การเขียนวิกิ* เป็นคนละหน้าที่

## 2. แต่ละสเตจ: input / output / failure modes

### 2.1 Ingest — นำเข้าและย่อย source

| ด้าน | รายละเอียด |
|------|-----------|
| **Input** | source ดิบหนึ่งชิ้น (ไฟล์/URL/บทสนทนา) |
| **ทำอะไร** | LLM อ่าน source, คุยสรุปประเด็นสำคัญกับผู้ดูแล, บันทึกต้นฉบับลง `raw/` แบบ **immutable**, เขียน **append-only log** ว่ารับอะไรเข้ามาเมื่อไร |
| **Output** | รายการ raw ใหม่ (พร้อม id/ที่มา) + คิวงานให้ synthesis |
| **Failure modes** | (1) แก้/เขียนทับ raw เดิม → เสีย provenance (2) ดูดเนื้อหาซ้ำซ้อนเข้ามา (3) OCR/แปลงไฟล์เพี้ยน (4) ไม่บันทึกที่มา → อ้างอิงกลับไม่ได้ |

> หลักเหล็ก: `raw/` **ห้ามแก้** มันคือ "ความจริง/ที่มา" (source of truth) ทุกหน้า wiki
> ต้องผูกกลับ raw ได้เสมอ — นี่คือ citation ภายในเล่ม (ดู [04-llm-wiki-library.md](04-llm-wiki-library.md))

### 2.2 Synthesis — เขียน/อัปเดตหน้า wiki ("การคอมไพล์")

| ด้าน | รายละเอียด |
|------|-----------|
| **Input** | raw ที่เพิ่ง ingest + หน้า wiki ที่มีอยู่ + schema |
| **ทำอะไร** | LLM เขียน **summary page** ของ source, อัปเดต **index**, แตะ **entity pages** และ **concept pages** ที่เกี่ยวข้องทั่วทั้งวิกิ, ร้อย **cross-link** ระหว่างหน้า |
| **Output** | ชุดหน้า wiki ที่เพิ่ม/แก้ (1 source ปกติแตะราว **10–15 หน้า**) |
| **Failure modes** | (1) เขียนทับความรู้เดิมหายโดยไม่ตั้งใจ (2) สร้างหน้าซ้ำแทนที่จะรวม (merge) (3) ลืมร้อยลิงก์ → เกิด orphan (4) สรุปเกินที่ raw รองรับ (hallucinate) (5) ไม่ทำตาม schema → โครงหน้าเพี้ยน |

> ทำไมเรียก "การคอมไพล์": raw = ซอร์สโค้ด, LLM = คอมไพเลอร์, wiki = ไฟล์ที่รันได้
> สเตจนี้คือตัวแปลงจากแหล่งดิบหลายชิ้นให้เป็น *intermediate representation* ที่อ่าน/ค้นได้

### 2.3 Lint — ตรวจสุขภาพวิกิ

ทำเป็น **รอบ ๆ** (เช่น รายสัปดาห์) ไม่ใช่ทุกครั้งที่ ingest ตรวจทั้งเชิง *โครงสร้าง* และ *เนื้อหา*:

| สิ่งที่ตรวจ | อาการ | วิธีแก้ |
|------------|-------|--------|
| **Contradiction** | สองหน้าระบุข้อเท็จจริงขัดกัน | ชี้แหล่ง raw, เลือกตัวที่ใหม่/น่าเชื่อกว่า, บันทึกเหตุผล |
| **Stale claim** | ข้ออ้างล้าสมัยเมื่อมี source ใหม่ | mark ว่าเก่า + ชี้ไปหน้าที่อัปเดต |
| **Orphan page** | หน้าไม่มีใครลิงก์ถึง / ไม่อยู่ใน schema | ร้อยลิงก์เข้าโครง หรือ merge/ลบ |
| **Missing page** | schema ระบุ slug แต่ไม่มีไฟล์จริง | สร้างหน้า stub หรือถอด slug |
| **Broken cross-link** | `[[slug]]` ชี้ไปหน้าที่ไม่มี | แก้ลิงก์ หรือสร้างหน้าปลายทาง |
| **Missing provenance** | หน้า wiki ไม่ผูกกลับ raw | เติม citation หรือตั้งคำถามว่าข้อมูลมาจากไหน |
| **Knowledge gap** | หัวข้อที่ schema คาดว่าควรมีแต่ยังว่าง | บันทึกเป็นช่องว่าง → ป้อนเป็นโจทย์ ingest/query |

> **Failure modes ของ lint เอง**: ตรวจถี่ไปจน LLM แก้วน, lint แก้เนื้อหาเชิงข้อเท็จจริง
> โดยไม่ตรวจกับ raw (กลายเป็นการ "เกลี่ย" ข้อมูลให้เนียนแต่ผิด), หรือ lint เงียบ ๆ ลบ
> หน้าที่ยังมีค่า — ควรให้ lint *เสนอ* การแก้และมีคน/รอบรีวิวก่อน apply กับเรื่องสำคัญ

### 2.4 Query — ถาม-ตอบและ file-back (จุดที่ทำให้ compound)

| ด้าน | รายละเอียด |
|------|-----------|
| **Input** | คำถามผู้ใช้ + วิกิที่สังเคราะห์ไว้แล้ว |
| **ทำอะไร** | LLM ค้นหน้า wiki ที่เกี่ยว, อ่าน, สังเคราะห์คำตอบ **พร้อม citation**; ถ้าคำตอบมีค่า ให้ **file back** เป็นหน้าใหม่ในวิกิ |
| **Output** | คำตอบที่มีที่มา + (บางครั้ง) หน้า wiki ใหม่ที่ feed กลับเข้า synthesis |
| **Failure modes** | (1) ตอบจากความจำ LLM ไม่ใช่จากวิกิ → hallucinate (2) ไม่ file-back → ความรู้ไม่ compound (3) file-back มั่ว → วิกิบวมด้วยขยะ (ต้องผ่าน lint) (4) citation ชี้ผิดหน้า |

> นี่คือเหตุผลที่ระบบ "สะสมความรู้": *การสำรวจของผู้ใช้* (query) ถูกเก็บเป็นสินทรัพย์
> เช่นเดียวกับ source ที่ ingest เข้ามา — แต่ทุกหน้าใหม่ต้องวนผ่าน lint เพื่อคงคุณภาพ

## 3. ตารางเทียบวิทยาการคอมพิวเตอร์ (Compiler Analogy)

เปรียบเทียบของ Karpathy: ระบบทั้งหมดคือ **คอมไพเลอร์สำหรับความรู้**

| สเตจ/ส่วน | เทียบกับซอฟต์แวร์ | เหตุผล |
|-----------|-------------------|--------|
| `raw/` | ซอร์สโค้ด (source code) | ของจริงที่เขียน/ดูแลเอง, immutable เป็นต้นทาง |
| **ingest** | การอ่านไฟล์เข้า build (preprocess) | รับ input เข้าสู่กระบวนการแปล |
| **LLM** | คอมไพเลอร์ (compiler) | ตัวแปลง raw → artifact |
| **synthesis** | การคอมไพล์ + linking | สร้าง/เชื่อมหน้า เป็น intermediate representation |
| `wiki/` | ไฟล์ที่รันได้ (executable) / IR | ผลลัพธ์ที่นำไปใช้/อ่าน/ค้นได้ |
| **lint** | เทสต์ + optimization pass | ตรวจคุณภาพ, จับ regression, เกลี่ยโครงสร้าง |
| **query** | รันไทม์ (runtime) | เรียกใช้ artifact ที่คอมไพล์ไว้ตอนถาม |
| `schema` | สเปก/config ของคอมไพเลอร์ (เช่น `CLAUDE.md`) | บอกว่าจะคอมไพล์อย่างไร โครงหน้าเป็นแบบไหน |

## 4. ต่างจาก RAG ธรรมดาอย่างไร (Stateful vs Stateless)

ประสบการณ์ LLM-กับ-เอกสารส่วนใหญ่คือ **RAG**: อัปโหลดไฟล์ → ตอนถามค่อยดึง chunk
ที่เกี่ยว → ตอบ ปัญหาคือ LLM **"ค้นพบความรู้ใหม่ตั้งแต่ศูนย์ทุกคำถาม" ไม่มีการสะสม**

| ประเด็น | RAG ธรรมดา (stateless) | **LLM-Wiki pipeline (stateful)** |
|---------|------------------------|----------------------------------|
| ความรู้เกิดเมื่อไร | ตอน query | **คอมไพล์ล่วงหน้าใน synthesis** |
| ผลลัพธ์ตกผลึกไหม | ไม่ — คำตอบหายไป | **เป็น artifact ถาวรที่ compound** |
| งานหนักอยู่ที่ | retrieval ตอนถาม | ingest + synthesis (เขียนวิกิ) |
| คุณภาพเมื่อใช้ไปนาน | คงที่ (ขึ้นกับ corpus) | **ดีขึ้นเรื่อย ๆ** (query → file-back) |
| ความขัดแย้งในข้อมูล | ไม่ถูกจัดการ | **lint จับและคลี่คลาย** |

> เปรียบ: RAG = ตีความซอร์สใหม่ทุกครั้งที่รัน (interpreter ที่ไม่ cache);
> LLM-Wiki = คอมไพล์ครั้งเดียวแล้วดูแลให้ทันสมัย (compiled + maintained)

**เมื่อไรใช้อะไร**

- ใช้ **RAG** เมื่อ: corpus ใหญ่/เปลี่ยนเร็วมาก, คำถามกระจายทั่ว, ไม่คุ้มจะคอมไพล์ล่วงหน้า,
  ต้องการตั้งระบบเร็ว
- ใช้ **LLM-Wiki pipeline** เมื่อ: หัวข้อมีขอบเขตชัด (= "หนึ่งเล่ม"), ต้องการความรู้ที่
  **สะสมและตรวจสอบได้**, มีผู้ดูแลคอย ingest/lint, ให้ความสำคัญกับ provenance และ citation
- ทั้งสองไม่ขัดกัน: query ในไปป์ไลน์นี้ **อาจใช้ RAG ดึงหน้า wiki** ที่สังเคราะห์ไว้แล้วได้
  (RAG เป็น *ทางเลือกของ retrieval* ไม่ใช่แกนของความรู้ — ดู [00-overview.md](00-overview.md) §0)

## 5. ความกังวลด้านคุณภาพรายสเตจ และการบรรเทา

| สเตจ | ความเสี่ยงหลัก | การบรรเทา |
|------|---------------|-----------|
| ingest | provenance หาย, ของซ้ำ | raw immutable + id/log, dedupe ก่อนเก็บ |
| synthesis | hallucinate, หน้าซ้ำ, orphan | บังคับ "เขียนจาก raw + ใส่ citation", merge แทน new, ร้อยลิงก์ตอนเขียน |
| lint | แก้วน, ลบของมีค่า | เสนอแก้ให้คนรีวิว, ตรวจเทียบ raw, รอบถี่พอเหมาะ |
| query | ตอบนอกวิกิ, file-back ขยะ | prompt ให้ "ตอบจากหน้า wiki เท่านั้น", หน้าใหม่ต้องผ่าน lint |
| ทั้งระบบ | scope creep ของเล่ม | คุมขอบเขตเล่มด้วย schema (ดู [02-llm-wiki-book.md](02-llm-wiki-book.md)) |

## 6. เช็กลิสต์รันไปป์ไลน์ให้ดี

- [ ] กำหนด **scope ของเล่ม** ให้ชัด ก่อนเริ่ม ingest (หนึ่งหัวข้อ = หนึ่งเล่ม)
- [ ] เขียน **schema** (กติกาโครงหน้า/พฤติกรรม LLM) เป็นไฟล์เดียวที่ทุกสเตจอ้างถึง
- [ ] ตั้ง `raw/` เป็น **immutable** + append-only log ทุกการ ingest
- [ ] ทุกหน้า wiki ต้องมี **citation ผูกกลับ raw** เสมอ
- [ ] synthesis: ให้ 1 source อัปเดต **ทุกหน้าที่เกี่ยว** (summary/entity/concept/index) ไม่ใช่หน้าเดียว
- [ ] ตั้งรอบ **lint** ประจำ (ขัดแย้ง/ล้าสมัย/กำพร้า/ลิงก์ขาด/provenance/ช่องว่าง)
- [ ] query บังคับ **ตอบจากวิกิ + อ้างอิง**, ปิด "ตอบจากความจำ"
- [ ] เปิด **file-back**: คำตอบดี ๆ กลายเป็นหน้าใหม่ → ผ่าน lint → compound
- [ ] มี **คน/รอบรีวิว** สำหรับการแก้เชิงข้อเท็จจริงที่สำคัญ
- [ ] วัดสุขภาพเล่ม: จำนวน orphan, ลิงก์ขาด, หน้าไม่มี citation = ใกล้ศูนย์
