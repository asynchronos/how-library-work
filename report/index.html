03

ไปป์ไลน์ ingest → synthesis → lint → query

Technicalผู้ใช้

"โรงงานผลิตเล่ม" 4 สเตจ + ลูปสะสมความรู้ (compounding) ที่ทำให้ stateful ต่างจาก RAG เส้นตรง

1

Ingest

นำเข้า+ย่อย source ทีละชิ้น, เก็บลง raw/ แบบ immutable + append-only log (เก็บ id/ที่มา)

2

Synthesis ("การคอมไพล์")

LLM เขียน/อัปเดต summary·entity·concept·index พร้อมร้อย cross-link; 1 source ปกติแตะ ~10–15 หน้า

3

Lint

ตรวจสุขภาพวิกิเป็นรอบ: ขัดแย้ง·ล้าสมัย·orphan·ลิงก์ขาด·ไร้ provenance·ช่องว่างความรู้ (lint เสนอ คนรีวิวก่อน apply กับเรื่องข้อเท็จจริง)

4

Query + file-back

ตอบ จาก wiki/ ที่สังเคราะห์ไว้ (ไม่ค้นสด raw) พร้อม citation; คำตอบดี → file back เป็นหน้าใหม่ → ความรู้ compound

Lint — สิ่งที่ตรวจ / อาการ / วิธีแก้

สิ่งที่ตรวจอาการวิธีแก้
Contradictionสองหน้าระบุข้อเท็จจริงขัดกันชี้แหล่ง raw, เลือกตัวที่ใหม่/น่าเชื่อกว่า, บันทึกเหตุผล
Stale claimข้ออ้างล้าสมัยเมื่อมี source ใหม่mark ว่าเก่า + ชี้หน้าที่อัปเดต
Orphan pageหน้าไม่มีใครลิงก์ถึงร้อยลิงก์เข้าโครง หรือ merge/ลบ
Broken cross-link[[slug]] ชี้หน้าที่ไม่มีแก้ลิงก์ หรือสร้างหน้าปลายทาง
Missing provenanceหน้า wiki ไม่ผูกกลับ rawเติม citation หรือตั้งคำถามว่ามาจากไหน
Knowledge gapหัวข้อที่ schema คาดว่าควรมีแต่ว่างบันทึกเป็นช่องว่าง → ป้อนเป็นโจทย์ ingest/query

RAG ธรรมดา (stateless) vs LLM-Wiki pipeline (stateful)

ประเด็นRAG ธรรมดา (stateless)LLM-Wiki pipeline (stateful)
ความรู้เกิดเมื่อไรตอน queryคอมไพล์ล่วงหน้าใน synthesis
ผลลัพธ์ตกผลึกไม่ — คำตอบหายไปเป็น artifact ถาวรที่ compound
งานหนักอยู่ที่retrieval ตอนถามingest + synthesis (เขียนวิกิ)
คุณภาพเมื่อใช้นานคงที่ดีขึ้นเรื่อย ๆ (query→file-back)
ความขัดแย้งไม่ถูกจัดการlint จับและคลี่คลาย
RAG = ตีความซอร์สใหม่ทุกครั้ง (interpreter ไม่ cache); LLM-Wiki = คอมไพล์ครั้งเดียวแล้วดูแลให้ทันสมัย — และทั้งสองไม่ขัดกัน: query อาจใช้ RAG หยิบหน้า wiki/ ที่คอมไพล์ไว้ (01 §4)
04

หนึ่งเล่ม llm-wiki-book + schema

Technicalบรรณารักษ์

หนึ่งเล่ม = raw/ + wiki/ + schema กับกฎ "หนึ่งเล่ม = หนึ่งหัวข้อ"

กายวิภาคของเล่ม (3 ส่วน)

ส่วนสถานะบทบาทเทียบหนังสือจริง
raw/immutable (อ่านอย่างเดียว)ที่มา/ความจริง — papers, โน้ต, โค้ด, บทสนทนาเอกสารอ้างอิงท้ายเล่ม/ภาคผนวก
wiki/regenerableหน้าที่ LLM สังเคราะห์ เชื่อมด้วย wikilinkเนื้อหาเล่มที่อ่านได้
schema (CLAUDE.md)กติกาบอก LLM ว่าโครง/ระเบียบ/เวิร์กโฟลว์เป็นอย่างไรแนวทางบรรณาธิการ (style guide)

ชนิดหน้าใน wiki/

🔖

entity page

สิ่งของ/ตัวแสดงเฉพาะ (เช่น leader, follower)

💡

concept page

แนวคิด/กลไก (เช่น leader-election)

📝

summary page

สรุปหัวข้อ/บท

⚖️

comparison page

เทียบสองสิ่ง (เช่น raft-vs-paxos)

🗂️

index.md

สารบัญ — ร้อยทุกหน้าเข้าโครง

🧾

log.md

append-only — บันทึกการเปลี่ยนแปลง/เหตุผล

กฎหัวใจ — "หนึ่งเล่ม = หนึ่งหัวข้อ/โดเมน" → ทำให้ lint แม่น, query คม, หยิบเข้าชั้นห้องสมุด/อ้างข้ามเล่มได้ (02 §3)

schema ตรึงอะไร (กันปัญหาอะไร)

schema กำหนดกันปัญหา
โครงไดเรกทอรี + ชนิดหน้าหน้าซ้ำ/วางผิดที่
กฎตั้งชื่อ (slug, kebab-case)wikilink ชี้ผิด
รูปแบบ citation ([^n]: raw/<id>#<loc>)provenance ขาด/ไม่นิ่ง
ขอบเขต (scope ทั้งใน/นอก)scope creep
กติกา lint + Do-NOTแก้วน/ลบของมีค่า
Versioning / identity (FRBR-aware): raw/ immutable (append-only) → regenerate wiki/ จาก raw/ ได้เสมอ; identity = หัวข้อ + ชุด raw/ ณ เวลาหนึ่ง + schema; เปลี่ยน raw/schema = edition (expression) ใหม่ของเล่มเดิม (02 §4, 06 §4)
05

ห้องสมุด & citation (หัวใจ)

Technicalบรรณารักษ์

หลายเล่ม + catalog คร่อมบน + citation ร้อยทุกเล่ม (intra-/inter-book, PID) — catalog ไม่ละลายขอบเขตเล่ม

citation 3 ระดับ

🔗

intra-book (page → raw)

ทุกหน้า wiki/ ผูกกลับชิ้น raw/ ที่เป็นที่มา (เชิงอรรถ/บรรณานุกรมท้ายเล่ม) · raw immutable = ชี้ได้เสถียร

📎

inter-book (bibliographic link)

claim ในเล่ม A อ้าง หน้าหนึ่ง ในเล่ม B — อ้างถึง ไม่ก๊อป (คง single source of truth)

🆔

PID 2 ระดับ (กัน link rot)

ลิงก์ชี้ที่ PID, resolver แปลง PID → path ปัจจุบัน

PID 2 ระดับ

ระดับตัวอย่าง PIDชี้ไปที่เทียบห้องสมุด
เล่ม (book)lib:book/distributed-systemsหนังสือทั้งเล่มเลขเรียกหนังสือ (call number)
หน้า (page)lib:book/.../page/raft@v3หน้า wiki หนึ่งหน้า (+เวอร์ชัน)เลขหน้า + ฉบับพิมพ์

หลักการห้องสมุดที่ยืมมา → สิ่งที่คอลเลกชันต้องมี

หลักการห้องสมุด (ยืมมา)สิ่งที่คอลเลกชัน llm-wiki-book ต้องมี
Cataloging + Dublin Core/MARCระเบียน metadata ต่อเล่ม (title, creator, subject, identifier, version)
Classification (DDC/LCC) + call numberหมวดหัวข้อ + "ที่อยู่" ของเล่มที่เรียงลำดับ+แทรกใหม่ได้
Authority control + controlled vocabชื่อ/หัวเรื่องแบบ canonical + alias → ค้นแล้วรวมศูนย์
Persistent Identifier (DOI/Handle/ARK)ID ถาวรต่อเล่ม/เวอร์ชัน → citation ไม่พังเมื่อย้าย
FRBR (Work→Expression→Manifestation→Item)แยกระดับ หัวข้อเล่ม/เวอร์ชันเนื้อหา/snapshot/สำเนา
Preservation (LOCKSS/Fixity/Migration)สำรอง + checksum + แผนย้ายฟอร์แมต
กฎทอง: catalog คงขอบเขตของแต่ละเล่ม (ไม่ละลายรวมกัน) — ดีกว่า "วิกิยักษ์ใบเดียว"; cross-book query = route → query/เล่ม → synthesize + แนบ citation ทุกเล่ม (04 §4–§5)
06

Worked example — Raft Consensus

Technicalผู้ใช้

สร้างเล่ม "Raft Consensus Algorithm" end-to-end ผ่านทุกสเตจ

นิยามเล่ม

รายการค่า
ชื่อเล่มRaft Consensus Algorithm
ขอบเขตleader election, log replication, safety — ไม่ครอบ Paxos/ZAB (อยู่เล่มอื่น)
PID เล่มlib:book/raft-consensus

เดินทั้ง 4 สเตจ

1

Ingest 3 source

S1 Raft paper (2014, Ongaro & Ousterhout) · S2 MIT 6.824 notes · S3 บล็อก visualization → เก็บ raw/ immutable + log

2

Synthesis

wiki/ มี entity (leader/follower/candidate), concept (leader-election/log-replication/safety), comparison (raft-vs-paxos), index, log — ทุกข้ออ้างมี [^n]: raw/<file>#<loc>

3

Lint รอบแรก

จับ 3 ปัญหาจริง (ดูตารางถัดไป)

4

Query + file-back

ถาม "ถ้ามี leader สองตัวพร้อมกันจะเกิดอะไร?" → ตอบจาก wiki/ พร้อม citation → file back เป็น concept/split-brain.md = compound

ผล Lint รอบแรก

ที่พบชนิดการแก้
comparison/raft-vs-paxos.md ไม่มีใครลิงก์ถึงorphanเพิ่มลิงก์ในส่วน Comparisons ของ index.md
safety.md อ้าง timeout "100ms" แต่ S2 ว่า "150–300ms"contradictionยึด S2, แก้ตัวเลข, บันทึกเหตุผลใน log
candidate.md กล่าวถึง "pre-vote" แต่ไม่มี citationmissing provenanceไม่มีใน S1–S3 → mark เป็น knowledge gap
หยิบเข้าชั้นห้องสมุดได้: catalog record (Dublin Core ย่อ): Subject=Distributed Systems/Consensus (DDC 004.x), Version=edition-1 (Expression) · เล่มอื่นจะ cross-book cite มาที่ lib:book/raft-consensus/page/leader-election ได้ (05 §7–§8)

ความเสี่ยง: A กับ B พูดต่างกัน · วิธีแก้: cross-book lint รายงาน + ตัดสินมีบันทึกเหตุผล · เจ้าของ: SME + Librarian
🔗 Link rot (PID พัง)+
ความเสี่ยง: ลิงก์ข้ามเล่มเสีย · วิธีแก้: PID + resolver; ตรวจ link health รายเดือน · เจ้าของ: Platform / SRE
📜 ลิขสิทธิ์/สิทธิ์ raw+
ความเสี่ยง: นำเข้า raw ที่ไม่มีสิทธิ์ · วิธีแก้: ตรวจสิทธิ์ก่อน ingest; license ใน metadata; access control ต่อเล่ม · เจ้าของ: Legal
🧹 Scope creep+
ความเสี่ยง: เล่มเบลอ/บวม · วิธีแก้: คุม scope ด้วย schema; อนุมัติ scope change · เจ้าของ: Product Lead
♻️ Lint over-correction / file-back ขยะบวม+
ความเสี่ยง: แก้วน/ลบของมีค่า/wiki บวมแต่คุณภาพตก · วิธีแก้: human-in-the-loop กับการแก้ข้อเท็จจริง; หน้า file-back ต้องผ่าน lint รอบถัดไป
Governance: no-citation, no-answer + raw=ความจริง (immutable) + lint รักษาสุขภาพ (ในเล่ม+ข้ามเล่ม) + version control ผูกกับ FRBR (Work=scope, Expression=เนื้อหา/schema, Manifestation=release) (08 §4)
